# 架构与数据流

砚台由同源前端、FastAPI 主后端和通过适配层接入的盲点实验室组成。前端呈现服务端返回的学习状态，主后端负责会话与持久化，模型调用在服务端完成。

## 模块职责

| 模块 | 位置 | 职责 |
| --- | --- | --- |
| 页面与交互 | `edu-agent/frontend/` | 首次备考信息、推荐确认、练习作答、反馈与安排展示 |
| React 展示组件 | `edu-agent/ui/` | 学习进程、引用卡片、交互与动效；不拥有独立业务状态 |
| HTTP 入口 | `edu-agent/backend/api/` | 参数检查、会话入口及服务调用 |
| 院校比较 | `edu-agent/backend/services/recommender.py` | 专业匹配、来源关联、资料缺口与规则比较 |
| 学习目标与安排 | `edu-agent/backend/services/journey.py` | 将时间、反馈和作答轨迹汇入后续学习安排 |
| 实验室主服务 | `edu-agent/backend/services/lab_service.py` | 业务调用、请求缓存、并发占用与原子保存 |
| 实验室适配 | `edu-agent/backend/lab_adapter/blindspot.py` | 在主站会话与独立学习模块之间转换数据，注入模型通路 |
| 学习模块 | `edu-agent/vendor/blindspot_lab/` | 学习阶段、题目、解释、规则材料与动态题校验 |
| 会话存储 | `edu-agent/backend/services/session_store.py` | SQLite 中的会话、版本、请求结果与在途占用 |

## 学习闭环

1. 用户提供备考条件，系统用已有院校快照形成比较；目标必须由用户确认。
2. 用户说明今天的学习打算，进入首题诊断。
3. 系统根据作答形成暂时判断，再用区分题检查不同解释。
4. 展示对应规则、原文引用及讲解，再换题验证。
5. 将对错、用户反馈和剩余时间纳入下一步安排；需要时继续下一轮。

判断只描述当前证据支持的本轮观察。答对、猜对和能迁移应用是不同信息；用户反馈不会追改已经记录的对错。

## 程序与模型的分工

程序掌握阶段推进、题目 ID、判分规则、版本、引用定位和请求幂等。模型组织受约束的反馈与解释，并在 live 后续轮次提出逻辑题候选。

动态生成限于 P/Q/R 表达式及已支持的逻辑规则。程序先限制语法和深度，再通过真值枚举检查唯一答案，同时核对允许的规则来源和精确引文。未通过的候选不写入会话题库。该校验覆盖有界题目的形式正确性和引用匹配，不能保证所有自由文本讲解都没有语义错误。

每个会话保存自己的动态题库，不向共享固定题库写入题目。新建 live 会话最多保存两道动态题、最多五轮；历史快照保留原有轮数语义，并继续受时间预算约束。

## 一次状态变更如何保存

客户端携带请求 ID 与预期版本提交动作。主服务在模型调用前占用当前会话，并在保存结果时核对版本与占用持有者；并发请求不能同时推进同一会话。完成后的同一请求 ID 返回缓存，不重复计分或生成。

等待超时与后台模型工作结束分别处理。在途工作尚未结束时占用继续续期，旧计算不能覆盖新持有者的结果；异常退出后按占用过期机制恢复可用性。更详细的实现位于 `lab_service.py`、`session_store.py` 和适配层，回归覆盖见 [验证说明](VALIDATION.md)。

## 资料与执行模式

院校目录和原始网页是随仓库保留的资料快照，不在启动时自动刷新。推荐先匹配专业，不把其他专业数据挪来补齐缺项。

学习材料目前为自编逻辑演示规则，材料属性与执行模式分开：自编材料可以由真实模型讲解，mock 流程也仍然只是模拟反馈。预置练习档案是演示案例，不当作真实用户积累。

`run.py` 统一设置 mock/live 模式并启动本机服务，两种模式默认使用不同 SQLite 文件。这里描述的是本地原型结构，未提供经验证的公网部署、账户权限或多人生产运行方案。
